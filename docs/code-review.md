# DLM v0.0079 코드 리뷰·방향 평가

검토 대상: `/research/dlm_v0.0079`, release `20261021T030429Z-24439`.
운영 소스·테스트·실행 이미지에는 수정하지 않았다. 재현 코드는 별도 프로세스에서
실행했으며 사용자 저장소를 열지 않았다. 검토 문서와 증거만 추가하였다.

## 결론

**연결된 단위의 요청·대기·통지·AND 결합을 조사하는 기반으로는 적절하다.
그러나 현재 학습은 주로 증명 메모화와 공식 이름 부여이며, 공간적 국소 가소성이나
일반적인 새 개념·규칙 형성까지 구현한 것은 아니다.**

기존43개 Python 테스트는 재실행에서도 모두 통과했다(78.993초).
추가 검사에서는 입력 검증에 의한 프로세스 종료와 여러 상태 전이 결함을 확인했다.
테스트 통과를 곧바로 실행기 전체의 안전성·완료성 증거로 볼 수 없다.
확인된 추가 사례는 `review-evidence/results.json`에 기록하였다.

## 발견 사항 — 우선순위 순

### 1. [P1] 잘못된 정의 signature가 REPL과 snapshot 검증을 SIGSEGV로 종료

위치: `src/dlm/space-definitions.l:4-7`,
`src/dlm/space-session.l:29-42`.

`d79-define`은 signature가 적절한 리스트인지 확인하기 전에
`(dlm-length sig)`를 실행한다. 다음 공개 명령이 거절되지 않고 프로세스를 종료했다.

```lisp
(space 'define 'd 42 '(top))
```

같은 입력이 스냅샷의 이벤트에 들어가도 전체 재생 검증이 SIGSEGV로 종료한다.
이는 reader 문법 오류가 아니다. 문법적으로 올바른 데이터의 의미 검증 경로에서
발생하며 두 재현 모두 shell 종료 코드139였다.

```lisp
(e79-snapshot? '(space-session79 1 () ((define d 42 (top)))))
```

수정 방향: `sq-signature?` 등 구조·타입 검사를 길이 계산보다 먼저 수행하고,
공개 전이의 거절 계약이 load/replay 경로에서도 유지되는지 검사한다.
이 재현은 임의 코드 실행 취약점을 입증한 것이 아니라, 검증 경로의 프로세스
안정성 결함을 입증한다.

증거: `review-evidence/invalid-definition.l`, `invalid-snapshot.l`.

### 2. [P2] 마지막 대안 이후에도 next가 작업을 waiting에 남김

위치: `src/dlm/space-execution.l:69-74,129-138`.

한 대안이 값을 반환하고, next 이후 마지막 대안이 실패하는 경우:

```lisp
((choose (((accept first)) ((fail no-more)))))
```

결과는 `waiting`, 남은 사건은0이었다. `s79-program-fail`이 이미 소비한 성공
분기(`done`)도 live로 세기 때문이다. `s79-program-resume`도 다음 대안이 있는지
확인하지 않고 작업을 waiting으로 바꾼다. 이는 명시적으로 보류된 분기와 달리
앞으로 재개할 일이 없는 미종료 상태다.

수정 방향: 아직 탐색할 수 있는 상태와 소비된 종료 상태를 구분하고, 대안 소진 시
`exhausted`로 전이한다. 마지막 성공 이후 next, 남은 실패, 실제 suspended 분기,
반복 next를 각각 회귀 검사한다.

증거: `review-evidence/lifecycle.l`, `lifecycle.out`.

### 3. [P2] 하위 작업 생성의 거절 원인이 사라져 정의 사용이 영구 대기

위치: `src/dlm/space-definitions.l:13-30`,
`src/dlm/space-learning.l:56-62,76-78`.

`d79-use`는 전제256개를 유효한 입력으로 받는다. 하지만 `d79-step`에서 정의 조건
또는 guard를 하나 추가하면 문맥이257개가 되어 하위 problem 검증에서 거절된다.
`i79-child-job`은 이 거절을 모두 `suspended`와 빈 하위 작업 이름으로 바꾸며,
상위 job은 실패 원인을 받지 못한다.

실제 관찰: 전제 검증 true, job waiting, unit suspended, result 없음, 남은 사건0.
예산을 더 주거나 입력을 기다려도 유효한 하위 작업이 저절로 생성되지 않는다.
깊은 body에 iff를 덧붙이는 경우도 같은 post-expansion 검증 경로를 점검해야 한다.

수정 방향: 자동 조건을 추가한 실제 problem을 제출 전에 검증하거나,
`invalid-input/context-limit` 같은 명시적 결과를 상위 작업에 전달한다.
재개 가능한 자원 대기와 영구적인 입력 거절을 같은 상태로 처리하지 않는다.

증거: `review-evidence/lifecycle.l`, `lifecycle.out`.

### 4. [P2] 여러 Beth 작업이 정의 개수 제한을 초과

위치: `src/dlm/space-learning.l:114-118,155-161`.

정의 제한64는 작업 제출 시에만 검사한다. 정의가63개인 상태에서 Beth 작업 두 개를
제출하면 둘 다 통과하고, 완료 시 각각 등록되어 정의가65개가 된다.
실제 스레드가 없어도 비동기 작업의 검사 시점과 등록 시점 차이로 발생한다.

수정 방향: 슬롯 예약 또는 완료 시 재검사를 수행하고, 공간 부족을 해당 작업의
명시적 incomplete/capacity 결과로 반환한다. 상수로 선언한 제한은 모든 생성 경로에
동일하게 적용해야 한다.

증거: `review-evidence/lifecycle.l`, `lifecycle.out`.

### 5. [P2] 보간 주석이 공유 증명 DAG를 다시 반복 전개

위치: `src/dlm/space-learning.l:27-48`.

`i79-annotation-step`은 동일한 child ID도 매번 방문한다. G3 실행과 인증서 추출에서
공유한 부분을 후속 주석 단계에서는 공유하지 않는다.

`F0=p`, `F(n+1)=F(n)∧F(n)`에 대한 `p ⇒ F(n)`의 관찰 결과:

| 깊이 | 인증서 노드 | 주석 사건 |
|---:|---:|---:|
|2|3|10|
|4|5|46|
|6|7|190|
|8|9|766|
|10|11|3070|

이 가족에서는 인증서 노드 수가 `d+1`인데 주석 사건 수는 `3*2^d-2`다.
이는 **압축된 증명 DAG 크기 기준**의 반복 전개이며, 완전히 펼친 문자열 공식 크기와
비교하여 지수 오버헤드라고 주장하는 것은 아니다.

수정 방향: `(node-id, left-colors, right-colors)`별 주석 메모화와 결과식 공유를
구현한다. 분할 색상이 다르면 같은 node ID라도 다른 주석이 필요하므로 단순히
ID 하나만으로 캐시해서는 안 된다. 동치인 반복식의 축약은 별도 정당화가 필요하다.
이는 정확도 경쟁보다 '계산 단위의 공유'라는 설계 원리를 후속 연산에도 유지하는 문제다.

증거: `review-evidence/annotation.l`, `annotation.out`.

## 구현 방향에 대한 평가

### 적절하게 구현된 부분

- 의무의 키에 signature·순서 있는 문맥·scope·library epoch가 포함된다.
  다른 가정의 증명을 무단으로 공유하지 않는 방향이다.
- 반복된 AND 전제가 같은 증명 ID를 사용해도 전제의 중복 횟수는 보존된다.
- 반모델은 상위 root에서도 확인한 뒤 전달한다. budget 실패를 부정으로 만들지 않는다.
- 새로운 경로의 보간은 진리표 투영이 아니라 증명 주석을 실제로 사용한다.
  두 결과 entailment와 Beth의 비공허성·유일성·양방향 정의를 다시 확인한다.
- 원래 Maru REPL, 이전 API/저장 형식, compiler 경로를 유지한다.
- 정상 명령마다 과거 전체 이력을 다시 실행하지 않고, 저장 시 prefix를 재생한다.
  기존 snapshot 상태 변조·lock·외부 파일 변경 검사는 통과한다.

### 주된 연구 질문과의 거리

| 관점 | 현재 구현 수준 |
|---|---|
|연결된 단위의 협동|요청·waiter 통지·AND 결합은 실제 국소 프로토콜로 구현됨|
|비결정적 실행|제한된 program 명령 언어에서 선택·보류·역추적을 지원함|
|바인딩과 추론|assume/ask는 연결되지만 bind는 일치 검사, define-local은 문맥 데이터임|
|학습|완료된 study 증명에서 조건부 부분 증명을 수집·원자 이름변환하여 재사용함|
|새 정의 형성|기존 compound goal에 새 이름을 붙임; 일반적인 새 술어의 의미 발견은 아님|
|공간성|xyz는 배치 metadata; 거리·이웃·전달 지연이 작동 규칙에 참여하지 않음|
|국소 가소성|학습이 전역 증명 순회·검증·라이브러리 추가에 의존함; 국소 활동만의 연결 갱신은 미구현|

따라서 현재 결과를 **명제 증명 데이터플로와 구조 재사용의 초기 실행 기반**으로
평가하는 것이 정확하다. 공간 속 활동에서 새로운 개념과 계산 구조가 자율적으로
생성되는 모델이 입증되었다고 평가하기는 이르다. 이는 성능 향상 부재 때문이 아니라,
아직 구현되지 않은 작동 원리가 있기 때문이다.

### 효율·유지보수의 추가 과제

- `space.l:9-13`의 ID/key 표는 선형 탐색과 경로 복사를 한다. ready queue 개선이
  전체 실행의 상수 시간 접근을 뜻하지 않는다.
- `space-learning.l:170-190`은 각 부분 증명마다 전체 인증서를 추출하고
  `p78-admit`으로 재검증한다. 라이브러리가 이미 꽉 찼거나 중복이어도 많은 작업을
  먼저 수행한다. 사건 한 번이 긴 전역 작업을 포함할 수 있다.
- 완료된 단위·작업·과거 library가 누적되고 global unit threshold에서 모든 작업이
  멈춘다. 장기 학습을 조사하려면 생존 데이터·재사용 데이터·폐기 가능 실행 상태를
  구분해야 한다. 현재의 bounded 조사라는 문서상 범위 안에서는 알려진 한계다.
- 레코드 필드가 정수 인덱스로 널리 접근된다. accessor와 상태 전이 표를 도입하면
  조건 누락과 수동 field 배치 변경의 위험을 줄일 수 있다.
- 저장 결과는 최신 dirty 여부와 분리해서 표시해야 한다. 현재 `e79-commit`은
  마지막 saved 상태를 무효화하지 않고, close/open도 save-result를 초기화하지 않는다.
- 기존 FLDx2 경로는 이전 실행기를 사용한다. 새 space의 probe 결과를 FLDx2나 일반
  프로그램 학습 성과로 옮겨 주장해서는 안 된다.

## 검증 결과의 해석

43개 기존 Python 테스트를 재실행했고 모두 통과했다. 새 코드에 해당하는 검사는
417개 시퀀트,100개 보간 쌍,6개 Beth 이론 및 정상적인 저장/재시작·분기 검사를
포함한다. 그러나 잘못된 타입, 마지막 대안 소진, 여러 작업의 완료 시 제한,
하위 작업 생성 거절, 공유 DAG 주석 비용은 충분히 다루지 않았다.

이번 추가 검사는 잘못된 논리 정답을 반환하는 반례를 찾은 것이 아니다.
입력 안정성·작업 생애주기·자원 계약·공유 보존에 대한 실제 결함을 찾았다.
또한3세대 compiler 재생성은 재현성 증거이며, 새 DLM 함수의 의미적 정확성 증명은
아니다. 기존 소스/테스트 hash manifest는 검토 뒤에도 그대로 일치한다.

## 권장 순서

1. signature 등 입력 검증을 길이/순회보다 앞세우고 load/replay의 거절 경로를 검사.
2. 작업 상태 전이 표를 명시: ready/waiting/suspended/answered/consumed/exhausted와
   invalid-input/incomplete의 차이를 정리하고 끝 상태 전달을 수정.
3. Beth 정의 등록의 예약/완료 시 제한과 정의 전개의 최종 입력 검증을 보완.
4. 분할 정보를 포함한 증명·주석 공유를 구현하고, 학습 중 재검증·추출의 중복 제거.
5. 그 위에서 바인딩·local definition이 실제 추론 요청과 구조 형성에 참여하도록 조사.

지금은 MLIR·실제 스레드·일반 FOL을 동시에 추가하기보다, 이미 선택한 국소 동작과
완료·실패·재개 의미를 정확하게 만드는 편이 연구 해석에도 유리하다.

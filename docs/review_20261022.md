v0.0079는 연결된 계산 단위의 **요청·대기·통지·AND 결합**을 조사하는 초기 실행 기반으로는 적절하다. 그러나 현재의 학습은 주로 완료된 증명의 메모화와 공식 이름 부여이며, 공간적 국소 가소성이나 일반적인 새 개념·규칙 형성까지 구현한 것은 아니다.

기존 Python 테스트 43개는 재실행에서 모두 통과했다(72.263초). 그러나 테스트 통과를 실행기 전체의 안전성·완료성 증거로 볼 수 없다. 기존 리뷰의 P1/P2 5건을 재확인했고, 추가로 **인증서 검증 실패가 작업을 영구 정지시키는 결함**을 확인했다.

## 발견 사항 — 우선순위 순

### 1. [P1] `d79-define`의 signature 검증 순서가 SIGSEGV를 유발

위치: `src/dlm/space-definitions.l:4-7`

```lisp
(if (not (and (sq-name? name) (not (s79-job s name)) (not (dlm-assoc name (dlm-nth s 12)))
              (< (dlm-length sig) 999) (< (dlm-length (dlm-nth s 12)) s79-definition-limit)
              (sq-formula? 'classical-prop-v1 body sig))) '(rejected definition)
```

`sq-signature?` 검증보다 먼저 `dlm-length sig`를 호출한다. 기존 리뷰는 `42` 사례를 기록했지만, 실제로는 **proper list가 아닌 모든 signature**에서 프로세스가 종료된다.

재현 결과:

| 입력 | 결과 |
|---|---|
| `(space 'define 'd 42 '(top))` | exit 139, SIGSEGV |
| `(space 'define 'd "abc" '(top))` | exit 139, SIGSEGV |
| `(space 'define 'd 'abc '(top))` | exit 139, SIGSEGV |
| `(space 'define 'd (cons 'a 'b) '(top))` | exit 139, SIGSEGV |
| 같은 입력이 포함된 snapshot event의 replay | exit 139, SIGSEGV |

즉 정수 하나의 문제가 아니라 **타입/구조 검증 전에 길이 계산을 하는 검증 경로 전체의 문제**다. 문법적으로 올바른 데이터의 의미 검증 경로에서 발생하며, reader 오류가 아니다.

수정 방향:

1. `(sq-name? name)`과 `(sq-signature? sig)`를 먼저 수행한다.
2. 그 다음 길이/개수 제한을 검사한다.
3. 마지막으로 body 공식 검사를 수행한다.
4. `space 'define`과 snapshot replay가 동일한 거절 계약을 갖는지 회귀 테스트한다.

`sq-signature?` 자체가 비정상 입력에서 total인지도 함께 확인해야 한다. 길이 계산을 안전한 검증기 뒤로 옮기는 것만으로는 replay 경로의 동일 계약이 보장되지 않는다.

### 2. [P2, 추가 발견] 인증서 검증 실패가 job을 `checking`에 영구 정지

위치: `src/dlm/space-execution.l:23-52`

`s79-check-step`은 인증서 노드 검증 실패 시:

```lisp
(s79-finish s id 'failed '(invalid-certificate))
```

또는 root 불일치 시:

```lisp
(s79-finish s id 'failed '(invalid-root))
```

로 check unit만 실패 처리하고, purpose로 연결된 job에는 결과를 전달하지 않는다. 반면 `s79-job-wake`는 검증을 시작할 때 job을 `checking`으로 바꾼다. 따라서 실패 시 job은 `checking`에 남고 이벤트 큐는 비게 된다.

재현 결과:

```text
(job-status checking result () check-status failed remaining 0)
```

이는 “검증 실패”가 정상적인 종료 결과로 전파되지 않는 생애주기 결함이다. purpose가 `(reuse ...)`인 경우에도 대상 proof unit이 `waiting`에 남을 수 있다.

수정 방향:

- check unit의 실패를 `s79-job-done` 또는 reuse 대상의 명시적 실패 결과로 전파한다.
- 작업 상태 표에 `checking → failed-check` 또는 `invalid-certificate` 종료 상태를 추가한다.
- `check` 실패, root 불일치, purpose 누락을 각각 회귀 테스트한다.

### 3. [P2] 마지막 대안 소진 후 `waiting`

위치: `src/dlm/space-execution.l:69-74,129-138`

`s79-program-fail`이 `done` 상태의 분기까지 “live”로 세기 때문에, 첫 성공 이후 마지막 대안이 실패해도 job이 `exhausted`로 가지 않고 `waiting`에 남는다. `s79-program-resume`도 남은 대안 유무를 확인하지 않고 job을 `waiting`으로 바꾼다.

재현:

```lisp
((choose (((accept first)) ((fail no-more)))))
```

```text
(exhaustion-status waiting remaining-events 0)
```

수정 방향:

- `done`/`consumed`/`answered`를 live에서 제외한다.
- 대안 소진 시 `exhausted`로 전이한다.
- `next`는 실제 재개 가능한 대안이 있을 때만 `waiting`으로 변경한다.
- 마지막 성공 이후 `next`, 남은 실패, 실제 suspended 분기, 반복 `next`를 각각 회귀 검사한다.

### 4. [P2] 하위 작업 생성 거절이 영구 대기로 변함

위치: `src/dlm/space-definitions.l:13-30`, `src/dlm/space-learning.l:56-62`

정의 사용 시 전제 256개는 유효하지만, 자동 조건/guard를 추가한 뒤 context가 257개가 되어 하위 problem 검증에서 거절된다. `i79-child-job`은 이 거절을 모두 `suspended` + 빈 하위 작업 이름으로 바꾸므로 상위 job은 실패 원인을 받지 못한다.

재현:

```text
(accepted-premises true job-status waiting result () unit-status suspended remaining-events 0)
```

수정 방향:

- 자동 조건을 추가한 **실제 problem을 제출 전에 검증**한다.
- `invalid-input/context-limit` 같은 명시적 결과를 상위 job에 전달한다.
- 재개 가능한 자원 대기와 영구적인 입력 거절을 같은 상태로 처리하지 않는다.
- 깊은 body에 iff를 덧붙이는 경우도 같은 post-expansion 검증 경로를 점검한다.

### 5. [P2] Beth 작업이 정의 개수 제한을 초과

위치: `src/dlm/space-learning.l:114-118,155-161`

정의 제한 64는 작업 제출 시에만 검사한다. 정의가 63개인 상태에서 Beth 작업 두 개를 제출하면 둘 다 통과하고, 완료 시 각각 등록되어 정의가 65개가 된다. 실제 스레드가 없어도 비동기 작업의 검사 시점과 등록 시점 차이로 발생한다.

재현:

```text
(declared-definition-limit 64 actual-count 65)
```

수정 방향:

- 슬롯 예약 또는 완료 시 재검사를 수행한다.
- 공간 부족을 해당 작업의 명시적 incomplete/capacity 결과로 반환한다.
- 상수로 선언한 제한은 모든 생성 경로에 동일하게 적용한다.

### 6. [P2] 보간 주석이 공유 증명 DAG를 반복 전개

위치: `src/dlm/space-learning.l:27-49`

`i79-annotation-step`은 동일한 child ID도 매번 방문한다. G3 실행과 인증서 추출에서 공유한 부분을 후속 주석 단계에서는 공유하지 않는다.

`F0=p`, `F(n+1)=F(n)∧F(n)`에 대한 `p ⇒ F(n)`의 관찰 결과:

| 깊이 | 인증서 노드 | 주석 사건 |
|---:|---:|---:|
| 2 | 3 | 10 |
| 4 | 5 | 46 |
| 6 | 7 | 190 |
| 8 | 9 | 766 |
| 10 | 11 | 3070 |

이 가족에서는 인증서 노드 수가 `d+1`인데 주석 사건 수는 `3*2^d-2`다. 이는 **압축된 증명 DAG 크기 기준**의 반복 전개이며, 완전히 펼친 문자열 공식 크기와 비교하여 지수 오버헤드라고 주장하는 것은 아니다. 분할 색상이 다르면 같은 node ID라도 다른 주석이 필요하므로 단순 ID 캐시로는 부족하다.

수정 방향:

- `(node-id, left-colors, right-colors)`별 주석 메모화와 결과식 공유를 구현한다.
- 동치인 반복식의 축약은 별도 정당화가 필요하다.
- 작업 큐를 `dlm-append`로 반복 확장하는 비용도 `cons`/reverse 기반으로 줄인다.

## 잘 구현된 부분

- 의무의 키에 signature·순서 있는 문맥·scope·library epoch가 포함된다. 다른 가정의 증명을 무단으로 공유하지 않는 방향이다.
- 반복된 AND 전제가 같은 증명 ID를 사용해도 전제의 중복 횟수는 보존된다.
- 반모델은 상위 root에서도 확인한 뒤 전달한다. budget 실패를 부정으로 만들지 않는다.
- 새로운 경로의 보간은 진리표 투영이 아니라 증명 주석을 실제로 사용한다. 두 결과 entailment와 Beth의 비공허성·유일성·양방향 정의를 다시 확인한다.
- 원래 Maru REPL, 이전 API/저장 형식, compiler 경로를 유지한다.
- 정상 명령마다 과거 전체 이력을 다시 실행하지 않고, 저장 시 prefix를 재생한다. 기존 snapshot 상태 변조·lock·외부 파일 변경 검사는 통과한다.

## 효율·유지보수 관찰

- `space.l`의 ID/key 표는 선형 탐색과 경로 복사를 한다. ready queue 개선이 전체 실행의 상수 시간 접근을 뜻하지 않는다.
- `space-learning.l`은 각 부분 증명마다 전체 인증서를 추출하고 `p78-admit`으로 재검증한다. 라이브러리가 이미 꽉 찼거나 중복이어도 많은 작업을 먼저 수행한다.
- 완료된 단위·작업·과거 library가 누적되고 global unit threshold에서 모든 작업이 멈춘다. 장기 학습을 조사하려면 생존 데이터·재사용 데이터·폐기 가능 실행 상태를 구분해야 한다.
- `e79-close`는 save 실패 시 lock과 path를 유지하므로 재시도만 가능하고 강제 정리 경로가 없다. close의 정리 계약을 별도로 명시하는 편이 좋다.
- 저장 결과는 최신 dirty 여부와 분리해서 표시해야 한다. 현재 `e79-commit`은 마지막 saved 상태를 무효화하지 않고, close/open도 save-result를 초기화하지 않는다.
- 레코드 필드가 정수 인덱스로 널리 접근된다. accessor와 상태 전이 표를 도입하면 조건 누락과 수동 field 배치 변경의 위험을 줄일 수 있다.
- 기존 FLDx2 경로는 이전 실행기를 사용한다. 새 space의 probe 결과를 FLDx2나 일반 프로그램 학습 성과로 옮겨 주장해서는 안 된다.

## design_20261021.md 읽기

`/research/design_20261021.md`는 **구현 완료 보고서가 아니라 연구 구상 기록**이다. 문서 첫머리에도 “제안 단계이며, 문서 저장이 구현 착수 승인을 의미하지 않는다”고 명시되어 있다.

핵심은 다음 한 문장으로 요약된다.

> 기호·관계·조건·실행 흔적이 연결되는 내부 상태 공간을 MLIR로 표현하고, 그 공간에서 계산하면서 기억을 형성하며, 형성된 기억이 다음 계산을 구성하게 한다.

문서의 주요 구분:

- **일반 지식**: 외부 문서·관측·실행 결과에 접지하되, 외부에서 얻었다는 이유만으로 참인 공리로 취급하지 않음.
- **하나의 메모리**: 지식·현재 실행 상태·과거 흔적을 별도 저장소로 분리하지 않고 같은 공간의 서로 다른 역할/문맥으로 표현. 단, 모든 흔적을 같은 종류의 사실로 취급하지는 않음.
- **흔적의 필수 정보**: 적용 조건, 의존 근거/규칙, 변수 대응/문맥, 임시 가정인지 정당화된 귀결인지.
- **Maru와 DLM의 분업**: Maru는 공간 계산의 일반 기능(단위, 연결, 바인딩, 활성화, 대기/재개, 문맥 보존 병합, 흔적 재사용, 공간 직접 읽기/변경), DLM은 그 위의 공리·지식·증명 규칙.
- **attention에서 가져오는 것**: 학습된 유사도로 정보를 섞는 것이 아니라, 현재 조건에 따라 연결 가능한 단위를 찾고 타입·관계·변수 대응·적용 범위를 확인하는 선택적 연결.
- **적분에서 가져오는 것**: 성공 횟수/점수 누적이 아니라 연역적으로 정당화된 구조의 누적. `K(t+1) = K(t) ⊔ Δ(t)`에서 병합은 문맥·의존관계를 보존해야 하며, 같은 근거의 반복은 참을 더하지 않고, 다른 가정의 결과를 무조건 합치지 않고, 근거 철회 시 의존 결과를 재검토해야 함.
- **MLIR 관련 주의**: MLIR IR 자체가 영속 메모리나 스케줄러가 아님. graph region의 나열 순서는 실행 순서가 아니며, graph region 의미는 포함하는 연산이 정의함. 흔적 기록이 상태를 바꾼다면 효과/의존관계를 명시해야 최적화가 제거하지 않음.
- **뇌 영감**: 선택적 활동·결합·기억·학습·통합의 **작동 규칙**에 대한 영감이며, 신경 동역학이나 학습된 신경 표현이 없는 상태를 완성된 neurosymbolic brain이라고 단정하지 않음.
- **남은 설계 질문**: 단위의 상태/입출력, 활성화 조건과 결과 전달, 변수·가정·문맥 바인딩/분리, 활동이 남기는 흔적과 다음 계산에서의 사용, 연결된 실행 구조가 새 계산 단위가 되는 논리 규칙, 이를 MLIR 타입/연산/의존관계와 Maru 런타임에 일관되게 표현하는 방법.

즉 문서의 중심은 “무엇을 저장할까”가 아니라 **“각 단위가 어떤 규칙으로 활동해야 남겨진 구조가 다음 사고를 구성하는가”**다.

| 실행 흔적이 기억이 됨 | 부분 구현. 완료된 증명 → `study` → 조건부 부분 증명 pattern, 정의 이름 부여. 일반 실행 trace를 재사용 단위로 만드는 것은 아님 |
| 조건 기반 활성화 | 구현. request key, ready queue, waiter, `expand`/`rule`/`poll`/`wake` |
| 대기와 재개 | 구현. `waiting`, `suspended`, `ask`, `resume`, `next` |
| 문맥 보존 | 부분 구현. scope, library epoch, ordered sequent, signature가 key에 포함됨. `bind`는 exact consistency이고 일반 unification은 아님 |
| 단위 간 협력/AND 결합 | 구현. 공유 child obligation과 dependency multiplicity 보존 |
| attention에서 영감을 받은 선택적 연결 | 미구현. 학습된 유사도나 조건 기반 routing이 아니라 명시적 request/pattern match |
| 적분적 누적 `K ⊔ Δ` | 부분 구현. library epoch와 정의 추가는 있음. 일반 merge, retraction, 의존 결과 무효화는 없음 |
| MLIR dialect | 미구현. `xyz`는 16×16×16 layout metadata일 뿐 의미/거리 routing에 참여하지 않음 |
| Maru built-in 런타임 | 미구현. DLM Lisp 모듈을 외부에서 load하고, persistence는 DLM의 snapshot/replay가 담당. 원래 REPL은 idle task로 연결 |
| 프로그램이 공간을 직접 읽고 변경 | 부분 구현. Lisp 함수와 `space` REPL 명령으로 가능하지만 typed dialect/region은 아님 |
| neurosymbolic brain | 해당 없음. 신경 동역학/학습된 신경 표현이 없으므로 구조적 유사성만으로 주장하면 안 됨 |

정리하면, v0.0079는 design 문서의 **“연결된 단위의 요청·대기·통지·AND 결합”** 부분의 초기 실행 기반으로는 의미가 있다. 그러나 design의 중심인 **MLIR 기반 내부 상태 공간, 실행 흔적의 재사용 단위화, retraction을 포함한 적분적 누적, 조건 기반 선택적 routing**은 아직 구현되지 않았다.

## 검증 결과의 해석

43개 기존 Python 테스트를 재실행했고 모두 통과했다. 새 코드에 해당하는 검사는 417개 시퀀트, 100개 보간 쌍, 6개 Beth 이론 및 정상적인 저장/재시작·분기 검사를 포함한다. 그러나 잘못된 타입, 마지막 대안 소진, 검증 실패의 결과 전파, 여러 작업의 완료 시 제한, 하위 작업 생성 거절, 공유 DAG 주석 비용은 충분히 다루지 않았다.

이번 추가 검사는 잘못된 논리 정답을 반환하는 반례를 찾은 것이 아니다. 입력 안정성·작업 생애주기·자원 계약·공유 보존에 대한 실제 결함을 찾았다. 또한 3세대 compiler 재생성은 재현성 증거이며, 새 DLM 함수의 의미적 정확성 증명은 아니다.

## 권장 순서

1. **입력 검증 순서 수정**: `d79-define`에서 `sq-signature?`를 `dlm-length`보다 먼저 수행하고, load/replay의 거절 경로까지 검사한다.
2. **작업 상태 전이 표 확정**: `ready/waiting/checking/suspended/alternative/done/consumed/exhausted/failed`와 `invalid-input`, `invalid-certificate`, `capacity`의 종료 의미를 명시하고, check 실패도 job에 전파한다.
3. **자원/정의 제한의 commit-time 재검증**: Beth 정의 등록, 단위 생성, context 확장 후 problem 검증을 보완한다.
4. **주석 메모화**: `(node-id, lc, rc)` 키와 결과식 공유를 구현하고, 학습 중 재검증·추출의 중복을 줄인다.
5. 그 다음에야 design 문서의 다음 단계인 **binding/unification, local definition의 추론 참여, retraction, trace-as-reusable-unit**을 조사한다. 지금 MLIR·실제 스레드·일반 FOL을 동시에 추가하면 현재의 생애주기/검증 결함이 더 커진다.

현재 코드는 “명제 증명 데이터플로와 구조 재사용의 초기 실행 기반”으로 평가하는 것이 정확하며, design 문서의 “공간 속 활동에서 새로운 개념과 계산 구조가 자율적으로 생성되는 모델”이 입증되었다고 보기는 어렵다.
